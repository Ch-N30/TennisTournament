# Отдельный матч — MVP

## Границы

Матчи → настройка → ведение → сохранённый результат. Турниры отложены,
их существующий код сохраняется. Профиль не обязан участвовать в матче.
Новые экраны на русском. Создание — кнопка «+» сверху справа, не вкладка.

## Правила и критерии приёмки

- Одиночный / парный состав; мужская / женская категория и парный микст.
  В миксте места каждой стороны фиксированы: мужчина, затем женщина.
- Имя и фамилия обязательны. Игроки имеют UUID; профиль привязывается
  отдельно по profileID. Совпадение имён не означает одинаковую личность.
- Снимок состава и правил фиксируется при старте. При смене категории или
  размера состава удаление заполненных несовместимых мест требует подтверждения.
- Один сет или до двух выигранных сетов. Учёт только выигранных геймов.
  Сет заканчивается при 6:0–6:4, 7:5 или 7:6 через тай-брейк при 6:6.
- Допустимый итог тай-брейка: 7:0–7:5 либо N:(N−2), где N ≥ 8,
  в любом направлении. Например, 8:4 недопустим: игра закончилась бы при 7:4.
- Решающий сет такой же; супер-тай-брейка и счёта 15–30–40 нет.
- Победный гейм/тай-брейк автоматически завершает сет и при необходимости матч.
- Последовательная отмена воспроизводит оставшуюся историю событий;
  отмена победного действия открывает матч снова, в том числе после перезапуска.

## Архитектура

Чистый Swift Domain хранит конфигурацию, историю и детерминированный счёт.
Repository — граница persistence; ViewModel публикует только сохранённые изменения.
Coordinator владеет отдельным PRNDS flow матчей. DI остаётся в composition root.

### Хранение и согласованность

- `LocalMatchRepository` — actor, единственный live-экземпляр на приложение.
  JustContainer регистрирует `any MatchRepository` со scope `.singleton`;
  фабрика только создаёт объект. ViewModel/Coordinator создаются на MainActor
  и получают готовый repository через init, без Container/Resolver.
- Файл `Application Support/TennisTournament/matches-v1.json` в sandbox приложения.
  JSON envelope имеет `version: 1`. Хранятся UUID, снимки участников, правила,
  даты создания/изменения/завершения, revision, текущий счёт, победитель и история.
  Статус однозначно определяется сохранённым winner; при чтении счёт сверяется
  с воспроизведённой историей, а даты и состав проходят валидацию.
- До первой записи отсутствующий файл означает пустое хранилище. Ошибки чтения,
  декодирования, неизвестная версия, дубликаты ID и неверная история дают ошибку.
  Файл заново читается перед каждой мутацией, чтобы не затереть повреждения.
  Если файл исчез после того, как repository видел его, это тоже ошибка.
- Чтение → проверка revision → применение действия → `.atomic` запись выполняются
  внутри одного actor без точек suspension. Сериализация рассчитана на один процесс
  и один live-repository; App Extensions и несколько процессов не входят в MVP.
- ViewModel блокирует повторный запрос до завершения текущего сохранения.
  При ошибке остаётся предыдущий счёт; доступны повтор сохранения и обновление.
  Конфликт ревизий требует обновления, а не перезаписи устаревшего снимка.
- Отмена удаляет последнее событие, пересчитывает счёт и увеличивает revision;
  отменённые действия не поддерживают redo. История сохраняется целиком.
- Матчи общие для устройства, без фильтра по текущему профилю. Редактирование
  профиля не изменяет снимки уже начатых матчей. Незавершённая форма настройки
  не сохраняется после выхода; сохранение начинается кнопкой «Начать матч».

### Навигация

`AppCoordinator` владеет `MatchesCoordinator`, а тот — отдельным PRNDS store,
ViewModel списка, текущей настройки и матча. Экраны получают ViewModel и callbacks.
После создания маршрут настройки заменяется матчем: «Назад» возвращает к списку.
Переход между вкладками сохраняет путь. Выход с экрана не завершает матч.
Турнирные URL отклоняются до auth-gating, не сохраняются как pending deep link;
`tennistournament://settings` работает по прежним правилам.

## Проверка

По явному запросу пользователя новые тесты не пишутся, существующие не меняются,
unit/UI-тесты и автоматические UI-прогоны не запускаются. Это исключение из
AGENTS.md, commands/add-feature.md и требований покрытия критических правил.
Сборка проверяет компиляцию, но не доказывает корректность поведения.
Фактически выполнено 08.09.2026: XcodeBuildMCP `build_sim`, workspace
`TennisTournament.xcworkspace`, scheme `TennisTournament`, Debug,
iPhone 17 Pro / iOS 26.5, `CODE_SIGNING_ALLOWED=NO` — успешно, без предупреждений
в финальном результате. `git diff --check` — без замечаний. Lock-файл пакетов
не изменён; тестовые файлы после фиксации прежней DI-базы не изменялись.
При промежуточной сборке Swift 6.3.3 падал в IRGen на передаче MainActor-метода
как setter в `Binding`; явные замыкания устранили сбой без изменения compiler flags.
Ручные критерии: состав/смена категории, старт, 6:5 → 7:5, 6:6 → тай-брейк,
отмена через границу сета/матча, восстановление после перезапуска и ошибки хранения.

Существующие тесты прежнего активного турнирного flow сохранены без изменений;
ожидания маршрутизации потребуется пересмотреть отдельной задачей перед возвратом CI-гейта.

### Ручной smoke-сценарий

1. Матчи → «+»: создать одиночный матч, заполнить игроков, попробовать пустые
   имена и «Добавить меня» дважды. Проверить совместимость пола профиля.
2. Переключить парный/микст; убедиться, что на каждой стороне мужчина и женщина,
   а отказ от подтверждения смены состава сохраняет все введённые значения.
3. Начать матч. Добавить 6 геймов одной стороне: результат 6:0, победитель;
   отменить последний гейм: матч снова идёт при 5:0.
4. В новом матче дойти до 6:5, затем 7:5. В другом — до 6:6:
   обычные геймы недоступны; 8:4 отклоняется, 8:6 даёт сет 7:6.
5. Формат до двух сетов: проверить переход к следующему сету, завершение при
   второй победе и отмену через границу сета и матча.
6. Вернуться к списку, открыть матч, перезапустить приложение: счёт, статус
   и отмена должны сохраниться. Сменить имя профиля: старые участники не меняются.
7. Проверить «Скоро будет», обычный профиль, отклонение турнирного deep link.
8. Для ошибок хранения использовать только копию данных на отдельном симуляторе:
   после резервной копии повредить JSON и убедиться, что загрузка/создание показывают
   ошибку и файл не заменяется. Вернуть резервную копию. Проверить ошибку записи,
   отсутствие визуально принятого гейма и повтор после восстановления доступа.
